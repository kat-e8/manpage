Swapping the Registrations

With the decision made — one gateway, user scope — this covers exactly what ran on this laptop to remove the old local-project registrations and replace them with cloud ones, and what came back when it was checked.

scope: user (all projects, this laptop) 2026-08-16
00

Starting state

claude mcp list showed three local-scoped entries, tied only to the ManPage project directory. Two were already broken from an earlier renaming pass done on this project (pointing at MCP routes that no longer existed); one — docker — was still working, but at the old local route rather than the cloud gateway.

NameOld targetState before swap
codercommandsold local /mcp routealready broken
postgresold local SSE /postgres-mcp/sse routealready broken
dockerlocal /docker-mcpworking, but local-only
01

Step 1 — remove the old registrations

remove, local scope
claude mcp remove codercommands
claude mcp remove postgres
claude mcp remove docker

All three confirmed removed from the local config scoped to the ManPage project — the only scope they had ever been registered at.

02

Step 2 — add the cloud registrations, at user scope

All three upstream MCP servers speak the same transport — MCP Streamable HTTP — proxied through the one gateway on clubuntu, so all three were added the same way, differing only in path:

add, user scope
claude mcp add --transport http codercommands http://clubuntu.dala-cirius.ts.net:8100/coder-commands-mcp -s user
claude mcp add --transport http docker http://clubuntu.dala-cirius.ts.net:8100/docker-mcp -s user
claude mcp add --transport http postgres http://clubuntu.dala-cirius.ts.net:8100/postgres-mcp -s user

All three confirmed "Added ... to user config", with no [project: ...] tag on any of them — the marker that a registration is local-scoped. Its absence is what confirms these landed at user scope instead.

03

Step 3 — verify: the swap wasn't actually done yet

claude mcp list is the standard check after any registration change. Here, it revealed the swap wasn't actually finished — all three new entries failed to connect, each with the same confusing error. That failure, and its real cause, is covered in full in doc 3.

NameNew targetFirst check

dockerhttp://clubuntu.dala-cirius.ts.net:8100/docker-mcp✘ failed — see doc 3
postgreshttp://clubuntu.dala-cirius.ts.net:8100/postgres-mcp✘ failed — see doc 3

The commands above were correct — path, transport, and scope all landed exactly as intended. What was missing was an authentication header the gateway had required all along, discovered only once these registrations were actually exercised.
