Unrelated Histories

Why the first push to a brand-new GitHub repo failed in both directions, how it was fixed, and how to not hit it again.

repo: kat-e8/manpage 2026-08-16
01

What happened

A local repo was initialized (git init, add, commit) independently of GitHub. Separately, the GitHub repo was created and a file was committed to it directly through the web UI, before the local repo ever pushed. By the time git push ran, both sides already had their own, separate commit — and neither push nor pull could reconcile them.

02

Two root commits, not one history

A git commit's identity includes its parent. Two commits made independently — even with identical content — are different objects with no ancestor relationship unless one was built from the other. Here, both sides had a genuinely different root: local's own git init commit, and GitHub's auto-created one.

03

Diagnosis, as it actually ran

the tell
$ git merge-base --is-ancestor origin/main HEAD
$ echo $?
1                                    # NO — confirmed divergence, not just "behind"

$ git log --oneline main             # local's own line
3a3156e initial commit

$ git log --oneline origin/main      # remote's own line
ee45929 Initial README.md with project details
414ae68 Initial commit

Two different root hashes on each branch's own line is the confirming signal — not "remote is ahead," but "remote was never derived from local at all."

04

The fix — force push, discarding the remote's commits

The remote's only content was a throwaway auto-created README — nothing worth preserving as separate history, and nobody else had pulled from it yet. Given that, the clean resolution was to make origin/main simply point at local's history instead, discarding 414ae68 and ee45929 outright.

git push --force origin main
Verified after: git fetch origin then git merge-base --is-ancestor origin/main HEAD returned true — single lineage confirmed, both branches at 3a3156e.
05

How to avoid this next time

The root cause was ordering: GitHub's repo already had a commit before the first push ever happened. Prevent that, and this can't recur.

  • If the remote ever does have commits you want to keep, git pull origin main --allow-unrelated-histories merges them properly instead of discarding — the option not used here, since this remote's content was disposable.
  • Force-pushing is safe only when nobody else has fetched the branch being overwritten. Once a second person or machine has pulled, a force push rewrites history out from under them.
