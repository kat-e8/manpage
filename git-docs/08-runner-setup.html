What GitHub Actions actually is

A push or a tag is an event. GitHub's own servers match that event against every workflow file's trigger, resolve the matching one into a concrete job — an ordered list of steps, fully expanded, nothing left to interpret — and place it in a queue. A runner is a separate agent process, living wherever it's installed, that polls GitHub asking for queued jobs matching its labels, and executes whatever it's handed. Everything in this document is about that agent: getting one installed, identified, and running permanently on clubuntu.

01

The download commands

GitHub's "New self-hosted runner" page generates a download block roughly like this:

mkdir actions-runner && cd actions-runner
curl -o actions-runner-linux-x64-2.XXX.X.tar.gz -L \
  https://github.com/actions/runner/releases/download/v2.XXX.X/actions-runner-linux-x64-2.XXX.X.tar.gz
tar xzf ./actions-runner-linux-x64-2.XXX.X.tar.gz
  • mkdir actions-runner && cd actions-runner — creates a fresh subdirectory and enters it. This is the line that caused a real problem later (§07) — run from inside a directory already named actions-runner, it nests one level too deep.
  • curl -o ... -L https://github.com/actions/runner/releases/... — downloads the actual runner agent: a self-contained package with the Runner.Listener and Runner.Worker binaries, a bundled Node.js (for helper scripts), and supporting files. -L follows redirects, since release assets are typically served from a CDN, not the URL you request directly.
  • tar xzf ... — extracts the tarball into the current directory: bin/, externals/, run.sh, config.sh, svc.sh, and more.

Nothing here talks to kat-e8/manpage yet — this stage only unpacks generic runner software. It doesn't know which repo it belongs to until configure runs.

02

The configure command

./config.sh --url https://github.com/kat-e8/manpage --token <TOKEN> \
  --name clubuntu --labels clubuntu --unattended --replace

config.sh is what actually contacts GitHub and turns generic runner software into this specific, identified runner. It exchanges the short-lived registration token for long-lived credentials, then writes two files that matter most: .runner (metadata — id, name, the labels it answers to) and .credentials / .credentials_rsaparams (an RSA keypair used for all future polling — the one-hour token from GitHub's UI is spent the moment this succeeds; from then on, this keypair is what proves identity).

FlagWhat it does
--urlWhich repository this runner attaches to
--tokenOne-time registration token from GitHub's UI, valid ~1 hour, spent on success
--name clubuntuDisplay name in the repo's Runners list — must be unique per repo
--labels clubuntuCustom label added on top of the automatic self-hosted/Linux/X64 ones — this is what runs-on: [self-hosted, clubuntu] actually matches against. Not optional; without it the workflows would never find this runner.
--unattendedSkip interactive prompts, use the flags given instead of asking
--replaceIf a runner is already registered under this name, take over the registration instead of erroring — needed in §07 when a stale registration was left behind
03

The docker group — and a name collision worth clearing up

usermod -aG docker ghrunner adds ghrunner to the Unix docker group. The Docker daemon listens on /var/run/docker.sock, a socket owned by root:docker — group membership is what lets a non-root user run docker compose build/push/pull/up without sudo on every single command. It's also, by the same token, effectively root-equivalent: anything that can talk to the Docker daemon can mount the host filesystem into a container it creates. Worth knowing, not a flaw specific to this setup.

Separately — GitHub Actions has its own feature that's also called "runner groups," used at organization/enterprise level to control which repos can use which runners. This document never touches that feature; it's a Unix group, unrelated, that just happens to share a name with a different GitHub concept.

04

What svc.sh actually is

svc.sh is bundled inside the downloaded tarball — it's not a separate GitHub tool. Its job is narrow: wrap the raw runner process as a systemd service, so it survives disconnects and reboots instead of dying the moment a terminal closes.

SubcommandWhat it does
install <user>Generates /etc/systemd/system/actions.runner.<org-repo>.<name>.service, with User= set to the given account and WorkingDirectory=/ExecStart= pointing at this exact install path. Enables it (starts on boot).
startEquivalent to systemctl start on the generated unit
statusWraps systemctl status for the same unit
uninstallRemoves the unit file, disables the service
05

Phase 1, what happened

Ran cleanly, exactly as planned — verified afterward via getent passwd ghrunner and stat /opt/actions-runner: the account existed with the correct home directory, correct group memberships, and the deploy directory's permissions were correctly bridged.

06

Phase 2, what happened

Straightforward — GitHub's UI generated a registration token. No command to log; the only artifact is the token itself, used once in phase 3 and never reused.

07

Phase 3, what actually happened

sudo -u ghrunner -i was the first thing tried — and it silently failed to do what was intended. ghrunner's shell is /usr/sbin/nologin (set deliberately in phase 1, to block any interactive login as that account) — and -i specifically asks sudo to launch the target user's own configured shell as a login shell. nologin refuses. The download and configure commands ended up running as the invoking user instead, from whatever directory that session happened to be in (/opt/docker/manpage, left over from the .env work) — creating a misplaced /opt/docker/manpage/actions-runner/ rather than anything inside /opt/actions-runner.

That registration was real, though — running ./run.sh manually confirmed a genuine "Listening for jobs" state, proving the token and configure step had actually succeeded against GitHub, just in the wrong location on disk.

08

Phase 4, what actually happened

The first svc.sh install ghrunner && svc.sh start appeared to succeed, but systemctl status showed inactive (dead) after only 52 seconds — exited cleanly (status 0), not crashed. The likely cause: .credentials had been created by the invoking user in phase 3, not ghrunner; when the service was configured to run as ghrunner, it couldn't read its own credential files and gave up quietly.

Correcting this meant unregistering, deleting the misplaced directory, and redoing phases 3–4 properly — which surfaced three more small obstacles in sequence, each with its own real cause:

ObstacleActual causeFix
sudo -u ghrunner -i againSame nologin block as phase 3sudo -u ghrunner bash — names a shell explicitly instead of asking sudo to resolve the account's own (blocked) one
GitHub's own mkdir actions-runnerRun from inside a directory already named actions-runner (ghrunner's home), nesting one level deepshopt -s dotglob; mv .../actions-runner/* ...; rmdir ... — flatten, including hidden .runner/.credentials
"runner exists with the same name clubuntu"The phase-3 registration was likely never cleanly removed (its own removal command also used the blocked -u ghrunner -i)--replace on config.sh — safely takes over the existing name
cd /opt/actions-runner as katlegoCorrect, intentional — that directory is 0750 ghrunner:ghrunner, and katlego was never bridged into that group (only the reverse)sudo -i — a root shell bypasses the permission wall entirely
sudo cd ... → command not foundcd is a shell builtin, not an executable — there's nothing for sudo to runNot something to fix, just to know — became moot once already root via sudo -i

With the directory flattened and a clean registration owned entirely by ghrunner, svc.sh install ghrunner && svc.sh start produced a genuinely persistent service this time.
