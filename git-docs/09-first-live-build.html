The First Live Build

The moment the runner came online, it started working through every push queued since this morning — and surfaced two real bugs the pipeline had never actually hit before.

00

What was actually happening

Every commit pushed to main today had already queued its own build job — there just wasn't a runner to claim any of them until it was finally installed and started (doc 8). The instant it went active, it began draining that backlog, one job per push, in order. The failure emails weren't a new problem appearing — they were the pipeline's genuine first execution, discovering things local testing never could, because local testing always had a real .env sitting in the working directory and a Docker daemon already configured to trust the registry.

01

Bug 1 — a fresh checkout has no .env

Every ${VAR} in docker-compose.yml needs a source. Locally, that's always been a real .env file sitting right there. A CI checkout is different — .env is gitignored on purpose (docs 2 and 7 both cover why), so it simply doesn't exist in the fresh clone the runner just checked out.

02

Bug 2 — the push itself, HTTPS vs. plain HTTP

With the parse error fixed, the build genuinely ran — all five images built successfully. The failure moved to the very last step: docker push, with http: server gave HTTP response to HTTPS client. Docker assumes any registry speaks HTTPS unless explicitly told otherwise; this registry has only ever spoken plain HTTP (§ established when .env was written — deliberately, relying on Tailscale for privacy instead of TLS).

This never surfaced from the dev laptop, because the dev laptop's own Docker was already configured to trust this registry — every manual docker push all along had that config quietly doing its job. clubuntu's own Docker daemon had never been told the same thing.

03

Why a restart was actually necessary

daemon.json is read once, at the moment dockerd starts — it isn't a live-reloadable file for a setting like this. Editing it on disk changes nothing about the daemon already running in memory; only a restart makes it read the file again and pick up the new trust list.

04

The real cost of that restart — and live-restore

By default, containers are tied to dockerd's own lifecycle — restarting the daemon restarts everything it manages, and clubuntu runs a dozen other projects' containers, not just this one. "live-restore": true changes that relationship: containers actually run under containerd, a lower-level daemon dockerd normally supervises; with live-restore on, containerd keeps them running independently even while dockerd itself restarts.

Verified after: all containers back within ~32 seconds, none lost, docker info confirms both clubuntu.dala-cirius.ts.net:5000 and live-restore active.
