git-mcp: reaching any repo, on any tailnet node, in plain English

A third remote-capable MCP server, alongside docker-mcp and postgres-mcp — same gateway, same tailnet, same "point it anywhere" idea, but git's own shape forces a genuinely different design underneath. Nothing in this doc has been built yet.

status: not implemented — plan only 2026-08-16
00

What's already solved, and what isn't

"Plain English instead of git commands" needs nothing new. That's what MCP + an LLM already does — "list containers on katmint" already becomes a structured list-containers(docker_host=...) call today, with no NLP layer inside docker-mcp itself. Whatever git-mcp exposes as typed tools gets the same treatment automatically.

"Point it at any tailnet node" is the real design problem — and git isn't like Docker or Postgres here. Docker has a native remote-daemon protocol (docker -H ssh://...); Postgres has a native network protocol (any client, any connection string). Git's working-tree commands — status, diff, commit — are inherently local filesystem operations. There's no "connection string" that gives you git status on a different machine's repo. The rest of this doc is about how to bridge that gap safely.

02

Target registry, not a free-form host string

Every tool takes a required target naming a server-side-registered alias — clubuntu, katmint, katlegog — never a raw ssh://user@host string the way docker-mcp's docker_host works. Two reasons this is the better shape specifically for git-mcp:

  • Closes an SSH option-injection edge case a free-form string allows: a hostname beginning with - can be read as an ssh flag, not a destination. An alias can never do that.
  • Gives a fixed place to record each target's shell dialect — critical because katlegog is Windows (see §03).

No "local" default exists. Unlike docker-mcp, which has a real local Docker daemon reachable via a mounted socket, git-mcp's own container has no meaningful repos on it — so even "target clubuntu" goes over SSH, a self-loop entry in the same registry as every other host.

03

The hard problem: safe remote command construction

Every tool ultimately runs ssh <destination> "git -C <repo_path> <args...>". SSH's protocol always re-joins the remote command into one string and hands it to the target's login shell — there is no argv-preserving remote-exec mode. That creates two independent risks, and both need addressing:

LayerRiskMitigation
1. Shell-metacharacter injectionA backtick or $( ) in a commit message gets executed by the target's shell instead of stored as textDialect-aware quoting: shlex.quote() for POSIX targets, a separate windows_quote() for cmd.exe — never assume one dialect, select via the target registry's os field
2. Argument-shape / flag injectionA perfectly shell-safe string can still be dangerous by position — a branch name of --upload-pack=... or a pathspec of --force gets parsed by git itself as a flag once it arrives intactStructural validation before quoting: reject any ref/branch/remote/pathspec starting with -, validate against git's ref-name grammar

CategoryTools

Excluded from v1force-push, reset --hard, clean -f/-fdx, rebase, commit --amend, history rewriting, force branch delete, tag -f, checkout --force, any raw passthrough command tool

Same rule docker-mcp/postgres-mcp already follow: the tool set itself is the allowlist. Nothing here is gated behind a runtime confirm=true flag, because nothing in this codebase works that way — dangerous operations are simply never implemented.

GIT_TERMINAL_PROMPT=0 on every network-touching call (fetch/pull/push) — without it, a target needing interactive git credentials hangs the MCP call forever with no TTY to prompt against. Paired with a 30s subprocess timeout.

06

Staged rollout: POSIX first, Windows gated

Implement and fully verify clubuntu + katmint (both POSIX, shlex.quote() covers them) before enabling the katlegog registry entry. windows_quote() gets its own explicit test cases — cmd.exe metacharacters & | < > ^ % — before that target goes live. Don't ship an unverified Windows quoting path silently alongside the proven POSIX one.

08

Verification plan

  • Read tools against real repos (safe, no mutation possible): this repo itself, on katlegog and its clone on clubuntu — confirms Windows-path handling even for read-only calls.
  • Write tools against a disposable scratch repo only — never this repo, never a real upstream remote. Bootstrap a bare repo + clone manually, exercise git_add/git_commit/git_push against it.
  • Deliberate injection test cases, not an afterthought: a commit message with shell metacharacters (should pass through as inert data), a branch name starting with - (should be rejected by validate_ref_name) — repeated with cmd.exe metacharacters once windows_quote() exists.
  • Confirm GIT_TERMINAL_PROMPT=0 actually prevents a hang against a credential-requiring remote.
  • Same deploy pipeline as docker-mcp: push → build, tag → deploy, confirm mounts via docker inspect, then test through the real mcp__git__* tools.
09

Known limitation, flagged not solved

push/pull/fetch against a real upstream (e.g. GitHub) depends on the target account's own git credentials (e.g. docker-mcp-svc's own SSH key or token) — a separate concern from the git-mcp→host SSH tunnel itself. Verification sidesteps this with a disposable bare-repo remote; making real-remote push/pull work for a given account is a follow-up, not part of this plan.
